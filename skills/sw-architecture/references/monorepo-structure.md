# Monorepo 배치 규칙 — MSA 기본 구조

목표 기본 구조 (pnpm + Cargo workspace):

```
web/                 ← 웹 프론트엔드
mobile/              ← 모바일 프론트엔드
desktop/             ← 데스크톱 프론트엔드
backends/{bff}/      ← BFF들 — 클라이언트(웹/모바일/데스크톱)의 유일한 진입점
server-apps/{svc}/   ← MSA 서비스들 — 비즈니스 도메인의 실제 소유자
packages/            ← 공통 유틸/계약 패키지 (proto, event 스키마, 생성 클라이언트 포함)
docs/{feature}/      ← 기능별 spec.md + plan.md
```

(프로젝트가 이행기라 옛 구조가 섞여 있을 수 있다 — 새 코드는 목표 구조를 따르고,
옛 구조를 만나면 strangler 방식으로 이관을 제안한다. 임의로 둘을 섞지 않는다.)

핵심 원칙: **배치는 목적(purpose)으로 결정한다.** MSA가 기본이므로 도메인 로직의
정착지는 그 도메인을 소유한 server-app이다. BFF는 얇게, 서비스는 자기 도메인만,
packages는 계약과 공용 유틸만.

## 배치 결정 순서

새 코드가 생길 때 위에서부터 검사하고, 처음 걸리는 곳에 넣는다:

1. **화면/UI 로직** → `web/` | `mobile/` | `desktop/` 해당 플랫폼 앱 안에.
   플랫폼 간 공유가 실제로 생기기 전까지 packages로 올리지 않는다.
2. **클라이언트가 호출하는 API 표면** → `backends/{bff}/src/api/{path}/`.
   BFF의 책임은 인증/인가, 요청 검증, 서비스 호출 조합(aggregation), 응답 DTO까지다.
   **비즈니스 규칙이 BFF에 들어가기 시작하면 잘못된 배치다** — 그 규칙을 소유한
   서비스로 내린다.
3. **비즈니스 도메인 로직** → 그 도메인을 소유한 `server-apps/{svc}/`.
   각 서비스의 README(목적/스코프)가 판정 기준. "그 서비스가 관련 데이터를 갖고
   있어서"가 아니라 **목적이 부합**해야 한다.
4. **2개 이상 유닛이 공유하는 유틸/계약** → `packages/`. 소비자가 1개인 동안은
   그 소비자 안에 둔다.

## src/api/{path} — API 경로 기반 디렉토리

BFF와 서비스의 HTTP API 코드는 feature/도메인 폴더가 아니라 **API 경로를 그대로
미러링하는 디렉토리 구조**를 쓴다:

```
src/api/
├── mod.rs
└── v1/
    └── deals/
        ├── mod.rs            ← GET/POST /v1/deals 핸들러 + DTO
        └── memos/
            └── mod.rs        ← GET/POST/DELETE /v1/deals/:id/memos 핸들러 + DTO
```

- 핸들러와 그 요청/응답 DTO는 같은 경로 디렉토리에 colocate한다. 엔드포인트가
  하나뿐인 경로에 handler/types/service 파일 3분할을 하지 않는다 — 파일 하나로
  시작하고, 커지면 그때 나눈다.
- URL 경로를 보면 파일 위치를 알 수 있고, 파일 위치를 보면 URL을 알 수 있는 것이
  이 구조의 존재 이유다. 경로에 없는 이름(managers/, handlers/, misc/)을 만들지
  않는다.
- 여러 경로가 공유하는 도메인 로직·저장 모델은 서비스 내 `src/`의 별도 모듈
  (예: `src/models/`, `src/domain/`)로 — 단, 공유가 실제로 생겼을 때 승격한다.

## 서비스 간 통신 — 이벤트 vs gRPC

전달 수단은 두 가지뿐이고, 선택 기준은 호출 의도다:

| 의도 | 수단 | 예 |
|---|---|---|
| "이 일이 일어났다, 관심 있으면 반응해라" (결과 불필요) | **Redpanda(Kafka) 이벤트** | 메모 생성됨 → notification이 구독해 알림 발송 |
| "이걸 해달라 / 이 값을 달라" (결과가 즉시 필요) | **gRPC** | BFF가 deal 서비스에 딜 조회 |

- **BFF → 서비스**는 대부분 gRPC다 (클라이언트가 응답을 기다리고 있으므로).
- **서비스 → 서비스**는 이벤트가 기본이다 — 시간 결합(temporal coupling)을 끊는 것이
  MSA를 하는 이유의 절반이다. 서비스 A가 B의 응답 없이는 자기 일을 못 끝낼 때만
  gRPC를 쓰고, 그 동기 의존이 늘어나면 경계가 잘못됐다는 신호로 읽는다.
- 이벤트는 **일어난 사실**을 과거형으로 명명한다 (`deal-memo.created`). 명령을
  이벤트로 위장하지 않는다 (`send-notification` 이벤트는 gRPC 호출이어야 했던 것).
- 같은 데이터가 필요하다고 다른 서비스 DB에 직접 붙지 않는다 — gRPC로 묻거나,
  이벤트를 구독해 자기 저장소에 필요한 만큼만 복제한다. 경계를 우회한 DB 접근
  하나가 서비스 분리를 무효화한다.

## 계약(Contract)은 packages에

서비스 간 합의를 표현하는 것들은 전부 `packages/`가 소유한다:

- **proto** — gRPC IDL + 생성 스텁. 서비스별 feature 게이팅으로 필요한 것만 링크.
- **event 스키마** — Kafka 이벤트의 타입/토픽 정의. producer와 consumer가 같은
  타입을 import하게 만들어 스키마 드리프트를 컴파일 타임에 잡는다.
- **생성 API 클라이언트** (ts-bridges류) — BFF 핸들러에서 생성된 typed 클라이언트.
  프론트는 이것만 경유하고, fetch URL 하드코딩·수동 타입 정의 금지. **DTO를 바꿨으면
  codegen 실행까지가 작업의 완료다.**
- 생성물은 손대지 않는다 — 소스(proto, 스키마, 매크로)를 고치고 재생성한다.

이벤트/proto 계약 변경은 **되돌리기 어려운 결정**이다 — 배포 순서(consumer 먼저
호환, producer 나중)와 하위 호환(필드 추가는 optional로)을 계획에 명시한다.

## 새 유닛 신설 기준

MSA 기본이라도 유닛 신설은 여전히 절제한다 — 서비스 수는 운영 비용에 비례한다.

- **새 server-app**: 기존 서비스 어디의 목적에도 안 맞는 **뚜렷한 비즈니스
  능력(capability)** 일 때. 엔드포인트 몇 개짜리 나노서비스를 만들지 않는다 —
  기존 서비스의 스코프 확장이 자연스러운지 먼저 본다. 신설 시 README(목적/스코프)
  작성 + 루트 문서의 서비스 맵 갱신까지가 신설 작업이다.
- **새 BFF**: 새 클라이언트 플랫폼/제품 표면이 생길 때만. 화면 몇 개 추가는 기존
  BFF의 `src/api/` 경로 추가다.
- **새 package**: 소비자가 이미 2개 이상이거나, 계약이거나, 생성물일 때만.

## Monorepo 리팩토링 신호

- BFF에 도메인 규칙이 쌓임 → 소유 서비스로 내리고 BFF는 조합만.
- 두 서비스가 항상 같은 PR에서 함께 바뀜 → 경계 재검토 (합치거나 계약을 다시 긋기).
- 서비스 간 동기 gRPC 체인이 3단 이상 → 이벤트 기반으로 재설계 검토.
- packages에 있는데 소비자가 1개 → 그 소비자 안으로 인라인 백.
- 이벤트 페이로드가 특정 consumer 전용 필드로 비대해짐 → consumer가 gRPC로 되묻는
  형태로 전환하거나 이벤트를 분리.
