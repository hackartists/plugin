# 점진적 리팩토링 플레이북

목표: **항상 동작하는 상태를 유지하면서** 구조를 개선한다. "멈추고 갈아엎기"는
리팩토링이 아니라 재작성이고, 재작성은 거의 항상 예상보다 비싸다.

## 철칙

1. **행동 변경과 구조 변경을 섞지 않는다.** 리팩토링 커밋에는 기능 변화가 없어야
   하고, 기능 커밋에는 구조 변화가 최소여야 한다. 섞이면 리뷰도 revert도 불가능해진다.
2. **모든 단계에서 green.** 각 단계 후 컴파일·테스트·(가능하면) 실행 확인. 빨간
   상태로 다음 단계에 넘어가지 않는다.
3. **테스트 없는 코드는 특성화 테스트부터.** 현재 동작(버그 포함)을 그대로 고정하는
   테스트를 먼저 만든다. 무엇이 "깨지지 않음"인지 정의되지 않으면 리팩토링이 아니라
   도박이다. E2E 한 개라도 없는 것보다 낫다.
4. **한 번에 한 가지 move.** 이름 변경 + 파일 이동 + 시그니처 변경을 한 커밋에
   섞으면 diff가 읽을 수 없게 된다.
5. **삭제로 끝난다.** 옛 코드가 남아 있으면 리팩토링은 끝난 게 아니라 중복을 하나 더
   만든 것이다. strangler 방식이라면 "옛 경로 삭제"가 계획의 마지막 단계로 명시돼야
   한다.

## 리팩토링 계획의 형태

리팩토링 요청을 받으면 실행 전에 이 형태의 계획을 만든다 (규모가 작으면 머릿속으로,
크면 문서로):

```markdown
## 목표 — 어떤 유지보수 문제를 없애는가 (한 줄)
## 안전망 — 기존 테스트 / 추가할 특성화 테스트
## 단계 — 각각 독립 커밋, 각각 green
1. [준비] 테스트 추가, seam 만들기
2. [이동] 새 구조로 옮기기 (호출처는 아직 옛 경로)
3. [전환] 호출처를 새 경로로 (여러 커밋으로 쪼개도 됨)
4. [삭제] 옛 경로 제거
## 하지 않는 것 — 이번에 건드리지 않는 범위 명시
```

"하지 않는 것"이 중요하다 — 리팩토링은 스코프가 새기 쉬운 작업이고, 스코프가 새면
2번 철칙이 무너진다.

## Smell → Move 카탈로그

| Smell | Move | 주의 |
|---|---|---|
| 거대 함수 (한 화면 초과) | 의미 단위로 함수 추출. 추출된 함수가 인자 5개+를 요구하면 데이터가 뭉쳐야 한다는 신호 → struct/객체로 | 추출 자체가 목적이 아니다 — 이름 붙일 수 있는 단위만 추출 |
| 거대 match/switch가 여러 곳에 반복 | 타입에 메서드로 이동 (Rust: enum method / TS: discriminated union + 함수 맵). 축이 "타입 추가"로 자주 늘면 그때 trait/다형성 | 한 곳에만 있는 match는 그냥 둔다 — match는 죄가 아니다 |
| god module/class | 책임별로 추출하되 기존 공개 표면은 facade로 유지 → 호출처 점진 이동 → facade 제거 | 한 번에 호출처 전부 바꾸지 않기 |
| 중복 코드 3회+ | 공통 함수/컴포넌트로 추출. 추출 전에 "정말 같은 이유로 바뀌는가?" 확인 — 우연히 닮은 코드의 추출은 잘못된 결합을 만든다 | |
| 순환 의존 | 공유 부분을 아래 계층(공용 모듈/계약)으로 추출하거나, 한 방향을 이벤트/콜백으로 역전 | |
| `-v2`/`-old` 병행 파일 | strangler 완주: 호출처 전환 → 옛 파일 삭제를 이번 작업으로 | 새 v3를 만들지 않는다 |
| 파라미터 목록 비대 | 의미 단위 struct/객체로 묶기 | 잡동사니 "Options" 백은 금지 — 의미 단위로 |
| dead code / 미사용 export | 즉시 삭제. git이 기억한다 | "혹시 몰라서" 금지. 주석이 "X에서 쓴다"고 주장해도 믿지 말고 `grep`으로 호출처를 실증 — 워크스페이스에 호출처가 없으면 삭제, 외부 crate/서비스가 쓸 가능성이 있으면 삭제 대신 보고 |
| 얕은 wrapper 계층 (한 줄 위임) | 계층 제거, 호출처가 아래 계층 직접 호출 | |
| 로직과 I/O 뒤엉킴 | 순수 로직을 함수로 추출 (데이터를 인자로) → 단위 테스트 부착 → I/O는 가장자리에 | hexagonal의 실용형 — port/adapter 격식은 불필요 |

## 큰 리팩토링: Strangler 순서

모듈/서비스 수준의 구조 변경은 항상 이 순서다:

1. **새 구조를 옛 구조 옆에** 만든다 (아직 아무도 안 씀 — 이 시점 배포 가능).
2. **호출처를 하나씩** 새 구조로 옮긴다 (각 단계 배포 가능, 문제 시 개별 revert).
3. 트래픽/호출이 전부 넘어가면 **옛 구조를 삭제**한다.
4. (선택) 새 구조 내부를 정리한다 — 이행기 동안 생긴 어댑터 제거.

이 순서의 요점은 각 단계가 **독립적으로 배포·검증·되돌리기 가능**하다는 것. 어떤
단계도 "며칠간 빌드가 깨져 있음"을 요구하지 않는다.

## 리팩토링을 제안만 해야 할 때

작업 중 발견한 개선거리가 현재 요청 범위 밖이면 — diff에 섞지 말고 보고한다:
"X를 고치다 보니 Y가 [smell]인 것을 발견. [move]를 별도 작업으로 제안" 형태.
이것이 SKILL.md Lean Rule 2(최소 diff)의 리팩토링 측 대응이다.
