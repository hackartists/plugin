# SW Architecture & Patterns — Lean Code 우선

이 스킬이 해결하는 문제: LLM 기반 개발은 **요청보다 많은 코드**를 만들어내는 경향이
있다 — 쓰이지 않을 추상화, 한 곳에서만 쓰는 helper, 기존 것과 중복되는 컴포넌트,
방어적 보일러플레이트. 이것이 쌓이면 유지보수가 어려워지고 점진적 리팩토링이
불가능해진다. 이 스킬의 모든 지침은 하나의 원칙에서 나온다:

> **코드는 자산이 아니라 부채다. 기능이 자산이다.
> 같은 기능이면 코드가 적을수록 좋다.**

## Lean Rules — 개발 모드의 핵심

코드를 쓰기 **전에** 아래를 따른다. 코드를 쓴 후 정리하는 것은 이미 늦다.

1. **재사용 우선 (search before write).** 새 함수/컴포넌트/타입을 만들기 전에 기존
   코드를 검색한다. 비슷한 것이 있으면 **확장이 기본, 신규 생성은 예외**다. 기존
   컴포넌트에 prop 하나 추가하면 될 일에 새 컴포넌트를 만들지 않는다.
2. **최소 diff.** 요청된 범위만 건드린다. 지나가다 눈에 띈 개선거리는 diff에 섞지
   말고 사용자에게 별도로 제안한다. 이유: 리뷰 가능성과 되돌릴 수 있음(revertability)이
   유지보수의 전제조건이다.
3. **추상화 3진법 (rule of three).** 첫 번째는 인라인으로 쓴다. 두 번째는 중복을
   허용한다. **세 번째 등장에서 추출한다.** "나중에 필요할 것 같아서" 만드는 추상화는
   금지 — 미래 예측은 대부분 틀리고, 틀린 추상화는 중복보다 비싸다.
4. **구현이 1개뿐인 인터페이스 금지.** trait/interface/제네릭 파라미터는 실제 두 번째
   구현이 있거나 외부 계약일 때만. "테스트를 위해서"는 concrete 타입으로 테스트가
   불가능함을 먼저 보인 뒤에만 유효한 이유다.
5. **새 파일의 자격.** 새 파일은 (a) 명확히 다른 책임이거나 (b) 프로젝트 컨벤션이
   요구할 때만 만든다. "helper.ts / utils.rs에 넣어두자"는 대부분 잘못된 배치 —
   쓰는 곳 옆에 두는 것(colocation)이 기본이다.
6. **삭제는 기능이다.** 작업 중 대체된 코드, 미사용 export/props/필드, 주석 처리된
   블록은 그 자리에서 지운다. git이 기억하므로 "혹시 몰라서" 남기지 않는다.
   `-v2`, `-new`, `-old` 접미사 파일이 공존하는 상태로 작업을 끝내지 않는다.
7. **기존 컨벤션이 정답이다.** 이웃 파일 2–3개를 먼저 읽고 네이밍·구조·에러 처리
   방식을 따른다. 컨벤션 자체가 문제라면 코드에서 바꾸지 말고 사용자와 논의한다.
8. **방어는 경계에서만.** 검증·null 체크·에러 래핑은 시스템 경계(API 입력, 외부 호출,
   파일/DB)에서 하고, 내부 함수끼리는 타입을 믿는다. 불가능한 케이스를 처리하는
   코드는 불가능하다는 사실을 숨기는 코드다.

### 코드 작성 직전 자가 점검

- 비슷한 기존 코드를 검색했는가? 확장 대신 신규 생성을 택했다면 그 이유를 한 줄로
  말할 수 있는가?
- 이 diff에 구현이 1개뿐인 추상화 계층이 있는가?
- 새로 만드는 파일 수가 기능의 크기에 비례하는가? (버튼 하나에 파일 4개는 실패)
- 요청 범위 밖의 변경이 섞여 있는가?

## 커맨드 연계 — 개발·설계 루틴에 내장

이 플러그인은 lean 원칙을 기계적으로 점검하는 두 커맨드를 제공한다. 스스로 지켰다고
믿지 말고 **루틴으로 실행**한다 (Skill 도구로 호출 가능, 사용자도 슬래시로 직접 실행):

| 커맨드 | 하는 일 | 언제 |
|---|---|---|
| `/hackartist-plugins:minimize-duplicates` | 범위 내 코드와 중복·유사한 기존 코드를 찾아 **기존 것을 호환 확장해 재사용**하도록 수정 | 새 코드 **쓰기 전**(탐색용) + **쓴 후**(정리용) |
| `/hackartist-plugins:minimize-changes` | diff의 모든 hunk가 목표에 필요한지 감사, 무관한 변경 되돌리고 더 적은 코드로 축소 | 구현 **완료 직후**, 커밋/PR 전 |

모드별 루틴:

- **개발 모드**: (1) 구현 전 `minimize-duplicates`로 재사용 대상 확인 → (2) 구현 →
  (3) `minimize-duplicates`(새로 쓴 코드 정리) → (4) `minimize-changes` → (5) 보고.
  (3)·(4)를 건너뛴 작업은 완료가 아니다.
- **리팩토링 모드**: 각 단계(커밋) 후 `minimize-changes` — 리팩토링은 스코프가 새기
  가장 쉬운 작업이다. 통합 단계에서는 `minimize-duplicates`의 호환 확장 규칙을
  따른다 (기존 호출처 무변경).
- **기획 모드**: 설계 문서의 단계별 계획에 "각 단계 완료 조건: minimize-duplicates →
  minimize-changes 통과"를 명시한다. 설계 단계에서 재사용 대상(기존 컴포넌트·서비스·
  계약)을 미리 찾아 문서에 적으면 개발 단계의 중복이 줄어든다.

두 커맨드 모두 "줄일 것/합칠 것이 없다"는 결론을 낼 수 있다 — 그것도 정상 결과다.
억지로 줄이거나 합치는 것은 또 다른 과잉이다.

## LLM이 특히 잘 저지르는 안티패턴

작성한 코드에서 이것들이 보이면 제출 전에 제거한다:

- **한 줄 위임 wrapper** — `fn get_user(id) { repo.get_user(id) }` 처럼 아무 것도
  더하지 않는 함수/메서드.
- **utils/helpers 파일 남발** — 응집 없는 잡동사니 모듈. 쓰는 곳 옆으로 옮긴다.
- **barrel file** (`index.ts` 재수출 전용 파일) — 순환 참조와 번들 비대의 원인.
  프로젝트가 이미 쓰고 있을 때만 따른다.
- **수동 타입 중복** — 생성된 타입(ts-bridges, ts-rs, codegen)이 있는데 손으로
  미러 타입을 정의. 생성 커맨드를 돌리는 게 답이다.
- **주석/독스트링 과잉** — 코드가 말하는 것을 반복하는 주석. 주석은 코드로 표현
  불가능한 제약·이유에만.
- **설정 과잉** — 호출처가 1곳인데 옵션 파라미터·config 객체·환경변수로 일반화.
- **성급한 최적화 장치** — 측정 없이 붙이는 memo/useCallback/캐시/pool.
- **에러 삼키기** — `catch (e) { console.log(e) }` / `let _ = ...` 로 실패를 숨기고
  진행. 처리할 수 없는 에러는 전파가 정답이다.

## 기획 모드

설계 문서(spec/plan)를 쓸 때도 lean 원칙을 적용한다 — **설계 단계의 과잉이 코드
과잉의 근원이다.** 필요한 힘(요구사항·규모·변경 축)이 없으면 계층·서비스·패턴을
추가하지 않는다.

문서 구조 (프로젝트에 기존 템플릿이 있으면 그것이 우선):

```markdown
# [기능명] 설계
## 컨텍스트 — 요구사항과 제약을 사실 위주로
## 결정 — 선택한 구조. 어디에 무엇이 들어가는지 (파일/모듈 수준)
## 고려한 대안 — 실제 대안 1–2개와 배제 이유 (허수아비 대안 금지)
## 단계별 계획 — 각 단계가 독립적으로 배포/검증 가능하게
```

설계 시 자가 점검:
- 새로 만드는 모듈/서비스/패키지마다 "기존 것 확장으로 안 되는 이유"가 있는가?
- 단계별 계획의 각 단계가 shippable한가? (1단계가 "전체 구조 재작성"이면 실패)
- 되돌리기 어려운 결정(스키마, API 계약, 서비스 경계)과 쉬운 결정(내부 구조,
  네이밍)을 구분했는가? 분석은 전자에 집중한다.
- 재사용할 기존 코드(컴포넌트·서비스·계약)를 찾아 문서에 적었는가? 각 단계의
  완료 조건에 `minimize-duplicates` → `minimize-changes` 통과가 들어 있는가?

## 패턴 선택 질문을 받으면

"어떤 패턴 써야 해?"류 질문에는 패턴 이름이 아니라 **그들의 코드로** 답한다:

1. 문제가 되는 실제 코드를 읽는다.
2. 패턴 없이 해결되는지 먼저 검토한다 (함수 분리, 데이터 구조 변경으로 충분한 경우가
   과반이다).
3. 패턴이 필요하면 해당 언어 reference의 smell → move 표를 참고해 그들의 코드에
   적용한 형태 + 도입 비용(간접화, 파일 수, 온보딩)을 함께 제시한다.
4. 지금 도입하지 않아도 되는 경우 — 그 사실을 명시하고 "언제 도입할지"의 트리거
   조건을 남긴다.
