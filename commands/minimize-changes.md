# minimize-changes — 변경 최소화 검증·축소

목표: **이 diff의 모든 hunk가 요청된 목표에 직접 기여하는가?** 기여하지 않는 변경은
되돌리고, 같은 목표를 더 적은 코드로 달성할 수 있으면 줄인다. 이유: 리뷰 가능성과
revert 가능성이 유지보수의 전제이고, 목표와 무관한 변경이 섞인 diff는 둘 다 잃는다.

`sw-architecture` 스킬의 Lean Rules(최소 diff, 추상화 3진법, 단일 구현 인터페이스
금지, 삭제는 기능)를 판정 기준으로 쓴다. 아직 안 읽었다면 먼저 읽는다.

## 1. 범위와 목표 확정

- 인자 `$ARGUMENTS`가 있으면: 목표 문장 / 경로 / 커밋 범위로 해석한다.
- 없으면: `git diff HEAD --stat` + `git status --short`(신규 파일 포함). working tree가
  깨끗하면 마지막 커밋(`git show --stat HEAD`)을 대상으로 한다.
- **목표를 한 줄로 다시 쓴다** — 대화 맥락/인자/커밋 메시지에서. 목표가 불명확하면
  diff를 보고 추정한 뒤 "이 목표로 판정합니다"라고 명시한다. 판정은 전부 이 한 줄
  기준이다.
- **삭제/교체 목표는 "대체가 필요한가?"를 먼저 확정한다.** "X 연동 제거" 같은 목표는
  두 가지 뜻이 있고 결과 코드베이스가 완전히 달라진다:
  - **대체 필요** (기능은 유지, 구현만 교체): 기존 모듈 경계 안에서 **내부 구현만
    바꾸고 호출처는 무변경**이 최소 diff다. 모듈을 지우고 호출처를 전부 고친 diff는
    호출처 hunk가 SHRINK 대상이다. 모듈 이름이 내용과 안 맞게 되면 이름 변경은
    SEPARATE (되돌리기 쉬운 결정, 별도 커밋).
  - **대체 불필요** (기능 자체 폐기): 모듈 삭제 + **호출처의 사용부 제거까지가 범위**
    이고 전부 KEEP이다 — 파일을 많이 건드려도 결과가 가장 작다. 이때 "대체 로직"을
    구현해 넣은 diff는 요구되지 않은 신규 코드이므로 SHRINK(삭제) 대상이다.
  - 대화에서 어느 쪽인지 판단이 안 서면 **추정하지 말고 사용자에게 묻는다.**

## 2. hunk 단위 감사

`git diff HEAD`(신규 파일은 내용 전체)를 파일·hunk 단위로 보며 각각 분류한다.
언어별 과잉 패턴 표는 `sw-architecture` 스킬의 `references/rust-patterns.md` /
`references/react-patterns.md`("흔한 과잉과 처방")를 판정 기준으로 함께 쓴다:

| 분류 | 기준 | 조치 |
|---|---|---|
| **KEEP** | 목표 달성에 필요 | 유지 |
| **SHRINK** | 목표엔 필요하지만 더 적은 코드로 가능 | 축소 |
| **REVERT** | 목표와 무관 (포맷팅, 이름 변경, drive-by 리팩토링, import 정렬, 주석 손질) | 되돌림 |
| **SEPARATE** | 가치는 있지만 별개 작업 | 되돌리고 후속 작업으로 보고 |

SHRINK 후보를 찾는 체크리스트 — 해당하면 줄인다:

- 신규 파일인데 기존 파일 수정으로 될 것 (새 컴포넌트 ↔ 기존 컴포넌트 prop 추가,
  새 util ↔ 쓰는 곳 인라인). 변경 전 파일 하나로 충분하던 규모(~300줄 미만)를 여러
  파일로 쪼갰다면 되돌려 합친다.
- 구현이 1개뿐인 trait/interface/제네릭/추상 클래스
- **같은 타입의 variant 분기를 다형성으로 바꾼 것** — enum variant마다 struct/handler
  를 만들고 trait + `dyn`/`Box<dyn>`으로 디스패치. 구현체가 3개여도 그것이 한 enum의
  variant들이면 과잉이다: enum 메서드(또는 함수 테이블)로 같은 중복 제거가 더 적은
  코드로 된다. trait은 **서로 다른 타입**이 같은 계약을 구현할 때만 정당하다.
- **리팩토링이 목표인데 LOC가 늘었다** — `git diff HEAD --shortstat`로 확인. 구조
  개선은 보통 코드를 줄인다. 늘었다면 추가분 하나하나를 목표로 정당화하거나, 더 단순한
  구조로 다시 짠다.
- 호출처가 1곳인데 옵션 파라미터·config 객체·feature flag로 일반화
- 한 줄 위임 wrapper, 재수출 전용 barrel 파일
- 불가능한 케이스를 처리하는 방어 코드, 내부 함수 간 중복 검증
- 코드를 반복하는 주석/독스트링, 미사용 import/변수/props/필드
- 측정 없이 붙인 memo/useCallback/캐시/pool
- 생성물(ts-bridges 등)을 손으로 수정한 흔적 → codegen으로 대체
- 목표에 요구되지 않은 추가 기능(수정 API, 정렬 옵션, "있으면 좋은" 필드)
- 테스트: 목표 동작을 검증하지 않는 테스트, 구현 세부를 고정하는 테스트

REVERT/SEPARATE 판정 시 주의: **삭제된 코드가 실제로 죽은 코드였는지** 확인한다
(`grep`으로 호출처 검증 — 주석이 "어디서 쓴다"고 주장해도 믿지 말고 실증). 호출처가
없으면 삭제는 KEEP이다. 반대로 목표에 "dead code 정리"가 포함돼 있는데 diff가 호출처
0건인 코드를 남겨 뒀다면, 그 삭제는 범위 **안**이다 — `pub`이라는 이유만으로 SEPARATE로
미루지 않는다 (외부 crate/서비스가 쓸 실제 근거가 있을 때만 보고로 대체).

## 3. 적용

- SHRINK/REVERT를 적용한다. SEPARATE는 이 diff에서 빼되 **버리지 않는다** — 내용을
  보고서에 남겨 사용자가 별도 작업으로 가져갈 수 있게 한다 (`git stash` 또는 patch
  파일로 보존해도 좋다).
- 되돌리기 전에 되돌릴 대상을 확인한다. 사용자가 직접 만든 변경이 섞여 있어 보이면
  되돌리지 말고 보고한다.
- 축소 후 **빌드·테스트·타입체크**를 다시 돌린다. 목표 동작이 여전히 충족되는지
  확인한다. 깨지면 해당 축소를 취소하고 그 사실을 보고서에 적는다.

## 4. 보고

```
## minimize-changes 결과
목표: <한 줄>
Before: N files, +A / -B   →   After: M files, +C / -D
### 줄인 것 (SHRINK/REVERT)
- <파일:위치> — <무엇을, 왜>
### 별도 작업으로 분리 (SEPARATE)
- <내용> — <보존 위치(stash/patch) 또는 제안>
### 유지한 이유가 필요한 것 (KEEP 중 논쟁 여지)
- <파일> — <왜 필요한지>
검증: build ✅ / test ✅ (또는 실패 내용)
```

줄일 것이 없으면 그렇게 말한다 — 억지로 줄이지 않는다. "이미 최소입니다" + 근거
한두 줄이 올바른 결과다.
