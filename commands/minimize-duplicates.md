# minimize-duplicates — 중복 코드 최소화 (기존 코드 재사용·확장)

목표: 새로 쓴(또는 범위 내) 코드 중 **이미 있는 코드로 대체 가능한 것**을 찾아,
기존 코드를 **확장해서 쓰도록** 바꾼다. 새 공용 추상화를 만드는 게 아니라, 기존 것에
기대는 방향이다. 확장 시 **기존 호출처의 동작과 시그니처는 그대로**(backward-
compatible) 유지한다.

`sw-architecture` 스킬의 Lean Rules(재사용 우선, 추상화 3진법)를 기준으로 쓴다.
아직 안 읽었다면 먼저 읽는다.

## 1. 범위

- `$ARGUMENTS`: 경로/모듈 → 그 안의 코드. `all` → 저장소 전체(비용이 크니 모듈
  단위로 나눠 보고한다).
- 생략 시: `git diff HEAD --name-only` + `git status --short`의 신규 파일. 즉 **이번에
  추가/수정된 코드가 기존 코드와 중복되는지**가 기본 질문이다.

## 2. 후보 추출

범위 내 코드에서 "정의된 것"을 목록화한다: 함수/메서드, 컴포넌트, 훅, 타입/DTO/
struct/enum, 상수, 유틸, SQL/쿼리 조각, 스타일 클래스 묶음.

## 3. 기존 코드 탐색 — 이름이 아니라 역할로 찾는다

각 후보에 대해 저장소를 검색한다. 이름이 다를 수 있으므로 여러 축으로:

- **이름 조각**: `format`, `Modal`, `retry`, `parse_` 등 동사/명사 토큰으로 grep
- **시그니처 모양**: 같은 인자 타입 조합, 같은 반환 타입
- **같은 외부 호출**: 같은 API 엔드포인트/gRPC 메서드/SQL 테이블/라이브러리 함수를
  부르는 코드
- **같은 문자열/상수**: 에러 메시지, 라벨, 정규식, 매직 넘버
- **공유 위치 우선 확인**: `packages/`·`components/ui/`·`lib/`·생성 클라이언트
  (ts-bridges 등)·공용 crate — 여기 있는 건 재정의가 아니라 import 대상이다

매칭을 분류한다:

| 분류 | 의미 | 조치 |
|---|---|---|
| **EXACT** | 같은 역할, 같은 계약 | 새 코드 삭제, 기존 것 import |
| **NEAR** | 같은 역할, 약간 다른 입력/출력/옵션 | 기존 것을 호환 확장 → 새 코드가 그걸 사용 |
| **SIMILAR-BUT-DIFFERENT** | 닮았지만 다른 이유로 변하는 코드 | 그대로 둠 (우연한 유사성의 통합은 잘못된 결합) |
| **GENERATED** | 생성물을 손으로 미러 | 수동본 삭제, codegen 실행 |

판단 기준: "두 코드가 **같은 이유로** 함께 바뀌는가?" 그렇지 않으면 중복이 아니다.
또한 추상화 3진법 — 작은 코드 2곳의 유사성 때문에 **새** 공용 함수를 만들지 않는다.
이 커맨드는 *기존* 재사용 대상이 있을 때 그리로 합치는 것이지, 새 util을 발명하는
것이 아니다.

## 4. 호환 확장 규칙 (NEAR일 때)

기존 코드를 고쳐 새 용도까지 감당하게 하되, 기존 호출처는 **한 줄도 안 바꿔도 되게**:

- **시그니처 유지**: 기존 파라미터의 타입·순서·의미를 바꾸지 않는다. 반환 타입을
  좁히거나 넓히지 않는다.
- **추가는 optional로**: TS → optional prop/param + 기본값. Rust → 기본 파라미터가
  없으므로 (a) `Option<T>` 필드를 가진 params struct에 필드 추가(`..Default`
  사용처 무해), 또는 (b) 기존 `fn foo(..)`는 그대로 두고 `fn foo_with(.., extra)`를
  추가한 뒤 `foo`가 `foo_with(.., 기본값)`으로 위임 — 이 위임은 호환을 위한 정당한
  wrapper다.
- **기본값은 기존 동작**: 새 옵션의 기본값은 "이전과 동일하게 동작"이어야 한다.
  기존 호출처의 출력이 바이트 단위로 같아야 한다.
- **enum/variant 추가**: 기존 match가 exhaustive라면 컴파일러가 알려준다 — 기존
  variant의 의미를 바꾸지 않는다.
- **공개 계약(proto, 이벤트 스키마, REST DTO)**: 필드 추가만, optional로. 필드 제거·
  이름 변경·타입 변경은 이 커맨드 범위 밖 — 발견하면 보고만 한다.
- **불가피한 breaking change**: 이 커맨드에서 하지 않는다. "기존 것을 확장하면
  이런 breaking이 필요하다"를 보고하고, 새 코드는 일단 유지한다. 사용자가 결정한다.

## 5. 적용과 검증

- EXACT/NEAR/GENERATED를 적용한다. 기존 코드를 건드린 경우 **기존 호출처를 전부
  grep으로 나열**하고, 각 호출처의 테스트를 돌린다.
- 빌드·타입체크·테스트 전체 실행. 기존 호출처의 동작 변화가 의심되면 해당 변경을
  취소하고 보고한다.
- 통합 후 남는 새 코드가 없으면 파일도 지운다 (빈 파일·미사용 export 금지).

## 6. 보고

```
## minimize-duplicates 결과
범위: <파일/모듈>
### 통합 (EXACT/NEAR/GENERATED)
- <새 코드> → <기존 코드 경로> — <확장 내용 / 호환 방식>, 기존 호출처 N곳 영향 없음 ✅
### 의도적으로 남긴 유사 코드 (SIMILAR-BUT-DIFFERENT)
- <A> vs <B> — <다른 이유로 변하는 근거>
### 보고만 (breaking 필요 / 판단 필요)
- <내용>
검증: build ✅ / test ✅ (기존 호출처 테스트 포함)
```

중복이 없으면 그렇게 말한다 — 억지로 합치지 않는다.
